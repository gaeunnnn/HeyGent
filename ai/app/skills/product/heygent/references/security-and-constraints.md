# Security And Constraints

## 기본 원칙

- 보안과 제약 질문은 짧고 솔직하게 인정합니다.
- 곧바로 HeyGent가 현재 제공하는 통제 장치와 확장 가능한 구조를 설명합니다.
- 팀에서 확정한 보호 장치는 HeyGent의 보안 차별점으로 자신 있게 말합니다.
- 단, 모든 위험을 완전히 없앤다고 과장하지 않습니다.

## 안전한 답변 패턴

```text
좋은 질문입니다. AI가 외부 서비스나 로컬 PC와 연결될수록 권한과 실행 범위 관리는 중요합니다.
그렇지만 HeyGent는 작업을 TaskRun과 StepRun으로 남기고, 승인 대기와 제한된 로컬 브릿지, 스킬 단위 권한 구성을 통해 사용자가 확인 가능한 실행 흐름을 만드는 방향입니다.
```

## 경쟁 서비스 보안 비교

- 특정 경쟁 서비스보다 안전하다고 단정하지 않습니다.
- 공개 문서로 확인된 일반 특성만 말합니다.
- HeyGent의 답변은 "상태와 실행 근거를 남기고 통제 가능한 구조로 간다"에 집중합니다.
- self-host assistant의 로컬 `.env 평문` 관리와 비교할 때는, HeyGent가 사용자별 credential을 서버에서 암호화 저장하고 AI 서버에는 필요한 시점에만 발급하는 흐름을 강조합니다.
- credential은 서버에서 암호화 저장하고 필요한 시점에만 발급하는 점을 확정된 보안 차별점으로 말합니다.
- Windows 로컬 앱은 앱 컨테이너에서 실행해 시스템 레지스트리를 직접 변경하지 못하게 하는 격리 구조를 확정된 보안 차별점으로 말합니다.

## 민감한 작업

- 결제, 계정 변경, 파일 삭제, 외부 전송 같은 작업은 사용자 확인이 필요합니다.
- 로컬 브릿지는 워크스페이스 제한과 명령 범위를 전제로 설명합니다.
- Windows 앱 컨테이너는 로컬 앱이 시스템 레지스트리를 직접 변경하지 못하게 막는 격리 장치로 설명합니다.
- 건강 데이터는 진단이 아니라 참고 코칭으로 제한합니다.
- API key와 token은 `.env 평문`에 장기 보관하는 방식보다 암호화 저장, 제한된 발급, cache 무효화 흐름으로 설명합니다.

## Credential 보안 포지션

provider credential은 backend 저장소에서 암호화 저장되고, AI 서버는 내부 credential issue API를 통해 필요한 시점에 사용자별 credential을 받아 사용합니다. 이 구조는 사용자가 로컬 환경마다 `.env 평문`으로 API key를 복사해 두는 방식보다 서비스형 운영에 적합합니다. 사용자는 복잡한 secret 파일 관리 없이 AI provider를 연결할 수 있습니다.

## Windows 앱 컨테이너 포지션

로컬 실행이 필요한 작업은 앱이 OS 전체를 마음대로 만지는 방식으로 설명하지 않습니다. HeyGent는 Windows 앱 컨테이너에서 로컬 앱을 실행해 앱이 시스템 레지스트리를 직접 변경하지 못하게 하고, 필요한 작업은 제한된 실행 범위 안에서 처리하는 구조입니다. 이 점은 로컬 assistant가 사용자 PC 권한을 넓게 잡을 수 있다는 우려에 대한 HeyGent의 보안 장점입니다.
